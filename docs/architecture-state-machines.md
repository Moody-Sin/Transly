# 桌面端与浏览器扩展任务状态机架构边界说明

本文档阐明 Transly 桌面端与浏览器扩展端两套任务状态机的语义设计与架构边界，解释为何不强行合并为同一套跨进程状态机。

## 1. 架构定位与执行环境差异

Transly 采用“中心调度桌面端 + 瘦客户端浏览器扩展”的分层模型：

| 维度 | 桌面端 (Tauri 宿主 + React) | 浏览器扩展 (Chromium MV3 + 原生 TS) |
| :--- | :--- | :--- |
| **执行环境** | 本地 Tauri 进程与主/浮窗 WebView | 浏览器后台 Service Worker 与各个独立网页 Tab 的 Content Script |
| **状态机粒度** | 单文本/单操作级别任务模型（`useTaskRunner`） | 整页 DOM 树数百个文本节点的批处理生命周期 |
| **生命周期** | 与窗口组件生命周期同步，毫秒级快速切换 | 跨 Popup 开启/关闭、跨网页动态 MutationObserver 持续监听 |

---

## 2. 状态机语义对比

### 桌面端状态机 (`TaskState`)
适用于主输入框、快捷键划词、系统剪贴板监听、浮窗：
- `idle`: 空闲就绪。
- `running`: 在途翻译中（支持通过代际 `generation` 丢弃迟到响应）。
- `succeeded`: 翻译成功并落地。
- `failed`: 失败，携带结构化 `ErrorKind` 与 `retryable` 判定。
- `cancelled`: 用户主动取消，状态冻结不回流。

### 扩展端状态机 (`TRANSLATION_PROGRESS`)
适用于网页整页原地替换：
- `translating`: 页面分批批量并发处理中，包含实时百分比与失败批次数。
- `finished`: 页面全部文本节点 100% 原地替换完成。
- `partially_failed`: 部分批次因网络/服务受限失败，自动激活“重试失败项”按钮。
- `cancelled`: 用户中断整页翻译，当前在途批次作废。
- `restored`: 页面通过 `WeakMap` 原文记录 100% 原地恢复为初始原文。

---

## 3. 为什么不跨进程合并状态机？

1. **避免跨进程高频状态同步的性能与复杂度爆炸**：网页包含大量节点，若强行让桌面端托管扩展每个 Tab 的逐节点生命周期，会引发大量 IPC 与 Localhost HTTP 心跳噪声。
2. **职责清晰**：桌面端负责**“单次翻译计算与安全凭据代理”**，扩展端负责**“网页 DOM 原地保真排版生命周期”**。
3. **高内聚低耦合**：即使扩展断开连接或 Popup 关闭，Content Script 与 Service Worker 的增量监听机制仍能独立保全 DOM 稳定性，不依赖桌面端 UI。
